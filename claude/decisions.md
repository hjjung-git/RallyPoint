# RallyPoint — 결정 사항

## 프로젝트 개요 (2026-10-12)
- RallyPoint는 사용자가 목표 프롬프트를 주면 그 목표에 맞는 프로젝트를 만들어 내는 도구다. Claude API 기반으로 여러 AI 세션이 역할을 나눠 협업한다.
- 세션 하나하나를 유닛이라 부른다. Planner가 목표를 서브태스크로 나누고 필요한 유닛을 구성해 지휘하며, 서버(오케스트레이터)가 실행을 조율한다.
- 컨셉은 스타크래프트 테란의 Commander와 SCV 역할 분담에서 착안한 메타포일 뿐이며, 프로젝트 안의 이름에는 쓰지 않는다.
- 이름 "RallyPoint"는 서브태스크를 알맞은 세션으로 보내는 라우팅 개념에서 따왔다.
- 정식 서비스 수준은 목표가 아니다. 다만 겉핥기로 끝내지 않고 하나의 시나리오를 완성도 있게 끝까지 만든다.

## 용어 원칙 (2026-10-12)
- 코드, 폴더, 문서, 대시보드 화면에는 유닛, Planner, Scheduler, Builder, Reviewer, Integrator, 오케스트레이터라는 중립적인 용어만 쓴다.
- 게임 용어는 이 문서의 개요 한 줄 외에는 어디에도 쓰지 않는다.

## 개발 환경 원칙 (2026-10-12)
- 개발 기기는 Mac과 Windows 두 대이며, 어느 쪽에서든 똑같이 동작해야 한다.
- 언어는 TypeScript(Node.js)로 통일한다. 서버와 대시보드가 같은 언어라 메시지 타입을 공유할 수 있다.
- Node는 22 이상이면 동작하도록 맞춘다. 기기마다 버전이 달라도 문제없게 하기 위함이다.
- 줄바꿈은 LF로 통일하고(.gitattributes), 에디터 설정도 통일한다(.editorconfig).
- OS에 따라 달라지는 셸 스크립트는 쓰지 않는다. 경로는 Node의 path API로 조합한다.
- API 키 같은 비밀 값은 리포에 넣지 않고 기기별 .env 파일로만 관리한다.
- Windows 기기에서의 clone과 환경 확인은 아직 하지 않았다. 접속 가능할 때 진행한다.

## 진행 방식 (2026-10-12)
- 칸반 방식을 기본 틀로 한다. 작업은 카드로 나누고, 카드는 할 일, 진행 중, 검토, 완료, 막힘 상태를 오간다.
- 유닛은 일을 배정받는 것이 아니라 놀고 있을 때 다음 카드를 가져간다(pull 방식). 이렇게 하면 Planner와 Scheduler의 부하가 줄어든다.
- 스크럼의 반복 개념을 얹는다. 목표를 한 번에 끝내지 않고 작은 반복으로 나눠 반복이 끝날 때마다 사용자에게 보고하고, 마지막에 회고(막힌 점과 잘된 점)를 정리한다.
- 대시보드는 그대로 칸반 보드가 된다. 유닛 수가 가변이어도 같은 화면으로 보여 줄 수 있다.

## 유닛 구성 (2026-10-12)
- 1차 스코프의 유닛: Planner, Scheduler, Builder, Reviewer, Integrator.
- Planner: 전체 컨텍스트를 갖고 계획을 세우고 전체를 지휘한다. 사용자와의 대화 창구이며, 진행 중 변수나 제약이 생기면 사용자에게 알린다.
- Scheduler: Planner와 유닛 사이에서 유닛의 전문성(역할 설명, 작업 범위, 실행 순서)을 조율한다. Planner의 부하를 줄이기 위해 두며, 필요할 때만 만든다. 한 단계만 두고 중첩하지 않는다.
- Builder: 맡은 범위 안에서 변경안을 만들어 제출한다.
- Reviewer: 다른 유닛의 결과를 읽기만 하고 완료 기준에 맞는지 판단한다.
- Integrator: 오케스트레이터가 감지한 충돌과 공유 파일의 변경안을 합친다.
- 유닛은 Planner가 필요한 만큼만 만든다. 유닛 수에는 상한을 두지 않고 동시에 실행되는 호출 수만 제한한다.
- 유닛은 명세서(역할, 작업 범위, 권한 수준, 보고 형식)를 받는 하나의 범용 구현이며, 유닛마다 별도 코드를 만들지 않는다.
- 각 유닛은 작업 범위가 제한된다. 범위를 제한하면 충돌은 공유 파일에서만 생긴다.
- 로드맵(1차 스코프 제외): Architect(구현 전에 공유 약속을 먼저 정하는 유닛, 효과를 보고 추가 여부를 정한다), 생성물을 실제로 실행해 검증하는 유닛(실행 보안 제한이 필요하다), 조사 유닛.

## 판단과 집행의 분리 (2026-10-12)
- 순서, 범위, 역할 같은 판단은 유닛(LLM)이 한다.
- 락, 버전 체크, 카드 배정, 동시 실행 수 제한 같은 집행은 오케스트레이터 코드가 한다. 유닛이 실수해도 파일이 덮어써지지 않게 하기 위함이다.
- 카드 배정은 선행 카드가 끝났는지와 동시 실행 한도가 남았는지를 규칙으로 확인해 코드가 건넨다. Scheduler는 카드의 순서와 명세서를 만드는 일만 한다.

## 실행 흐름과 메시지 종류 (2026-10-12)
- 계획과 승인: Planner가 유닛 구성, 카드, 순서, 예상 호출량을 사용자에게 제안하고 사용자가 승인하거나 수정을 요청한다. 실행은 승인 후에 시작한다.
- 준비: 유닛 생성(명세서)과 카드 등록(선행 관계 포함)을 오케스트레이터에 전달한다.
- 작업 진행: 유닛이 작업 요청을 보내면 오케스트레이터가 카드를 배정한다. 유닛은 변경안(파일, 기준 버전, 내용)을 제출하고 오케스트레이터가 적용하거나 거부한다. 카드 완료와 막힘 보고가 있다.
- 검토와 충돌: Reviewer가 통과 또는 반려를 보고하고(반려되면 카드가 할 일로 돌아가 다시 배정을 기다린다), 충돌이 감지되면 Integrator에게 넘기고, Integrator는 통합 결과 또는 해결 불가를 보고한다.
- 변수 발생: Planner가 사용자에게 이슈와 선택지를 알린다. 전체를 일시정지하고 사용자의 답을 기다린 뒤 재개한다. 일시정지 때는 진행 중인 호출을 끝까지 받고 새 호출만 시작하지 않는다. 읽기만 하는 유닛(Reviewer)은 진행할 수 있으며, 재개할 때 계획이 바뀌었다면 그 검토 결과를 다시 확인한다.
- 반복과 회고: 반복이 끝날 때마다 사용자에게 보고하고 확인받으며, 마지막에 회고를 정리한다.
- 대시보드 이벤트: 카드 이동, 유닛 상태 변경, 충돌 발생과 해결, 일시정지와 재개, 누적 호출량을 오케스트레이터가 대시보드로 보낸다.
- 비용 관리: 별도의 예산 한도는 두지 않는다. 사용자 확인 단계에서 예상 호출량을 보여 주고, 실행 중에는 대시보드에 누적 호출량을 표시만 한다.

## 시나리오 템플릿 (2026-10-12)
- 사용자는 시나리오 파일(Markdown)로 목표를 준다. 제목으로 구분된 섹션은 목표(필수), 제약(선택), 완료 기준(선택)이다.
- 제약이 비어 있으면 Planner가 기본값을 제안한다. 완료 기준이 비어 있으면 Planner가 제안하고 사용자가 계획 확인 단계에서 승인해 확정한다.
- 작업 폴더는 시나리오 파일에 적지 않고 실행할 때 사용자가 지정한다. 기기마다 경로 형식이 달라서, 이렇게 하면 같은 시나리오 파일을 두 기기에서 쓸 수 있다.
- 시나리오 파일은 리포의 scenarios 폴더에 둔다. 샘플을 올려 두어 결과물 시연과 README에서 보여 준다.
- 결과물은 사용자가 정한 작업 폴더에 만들어지며 이 리포에는 올리지 않는다.

## 1차 스코프 (2026-10-12)
- 포함: 시나리오 입력, 위 유닛 구성, 칸반 방식의 실행과 일시정지, 락과 버전 체크 수준의 공유 상태, WebSocket 기반 실시간 대시보드(가변 개수의 유닛 표시), 끝까지 동작하는 데모 시나리오 1개, 기본적인 에러 처리(세션 실패 시 재시도와 보고).
- 핵심 장면: 서로 다른 유닛이 같은 공유 파일을 동시에 건드릴 때 충돌을 감지하고 조정하는 것이다.
- 제외(추후 로드맵): 멀티유저, 인증, 멀티테넌시, 기존의 임의 코드베이스를 분석해 수정하는 기능, 상시 구동 배포와 스케일링, 생성물 실행 검증.

## 검증 방식 (2026-10-12)
- 별도의 고정 연습 코드는 두지 않는다. 시나리오 파일로 RallyPoint를 직접 실행해 보는 것이 기본 검증이다.
- 생성 결과는 실행마다 달라서 충돌이 항상 생기지는 않는다. 그래서 충돌 감지는 생성 결과와 무관하게 결정적으로 동작하도록 만들고, 시나리오 제약에 여러 기능이 공유 파일을 함께 쓰게 설계한다는 조건을 넣어 충돌 가능성을 높인다.
- API를 부르지 않는 결정적 로직(락, 버전 체크, 카드 배정)에 한해 자동 테스트(node --test)를 둘지는 필요해질 때 다시 판단한다.
- 마무리 데모는 RallyPoint가 어느 정도 완성된 뒤, RallyPoint로 새 프로젝트를 만드는 모습을 보여주는 방식으로 한다. 주제는 그때 정한다.

## 아키텍처 결정 (2026-10-12)
- 유닛은 파일을 직접 수정하지 않고 변경안을 서버에 제출한다. 서버가 파일 버전을 확인한 뒤 적용한다. 충돌 감지가 정확해지고, 파일 경로 처리를 서버 한 곳에서만 하면 되기 때문이다.
- 폴더 구성은 npm workspaces로 묶는다: packages/shared(공유 타입), packages/server(오케스트레이터), packages/dashboard(React, 추후 추가).

## 기존 멀티에이전트 프레임워크와의 차별점
- CrewAI, AutoGen, LangGraph를 개발 내내 계속 검토한다.
- UX나 기술적 제약 때문에 직접 오케스트레이션이 필요한 지점이 생기면 그 이유를 이 문서에 기록한다.

## 일정감
- 처음의 3~4주 추정은 유닛 수와 역할이 고정된 스코프 기준이었다. 유닛 가변 구성, 칸반과 반복 구조가 추가되어 설계가 더 구체화된 뒤 다시 어림한다.

## API 키 관리 (2026-10-12)
- 환경 변수 파일은 Node의 --env-file 옵션으로 읽는다. 별도 라이브러리 없이 Mac과 Windows에서 동일하게 동작한다.
- .env.example에는 변수 이름만 적어 두고, 실제 키는 기기별 .env에만 둔다.
- Claude 구독과 API Console은 결제가 별개이므로 API 크레딧은 Console에서 따로 관리한다.

## 공유 타입 (2026-10-12)
- 카드, 유닛 명세서, 메시지, 대시보드 이벤트의 타입은 packages/shared에 정의하고 서버와 대시보드가 같이 쓴다.
- 데이터 안의 파일 경로는 항상 슬래시(/)로 적는다. 실제 파일을 여는 서버에서만 Node의 path API로 변환한다. Mac과 Windows에서 같은 값으로 인식하기 위함이다.
- 유닛 권한 수준은 읽기만 / 변경안 제출 두 가지로 시작한다.

## 칸반 보드 규칙 (2026-10-13)
- 보드 로직은 packages/server/src/board에 둔다. Claude API를 부르지 않는 순수한 코드이며, 카드 상태는 메모리에만 저장한다.
- 카드 배정 조건: 상태가 할 일이고, 유닛 종류가 맞고, 선행 카드가 모두 완료여야 한다. 검토 중인 선행 카드는 아직 완료로 보지 않는다. 같은 조건이면 반복 번호가 낮은 카드를 먼저 준다.
- 동시 실행 한도는 진행 중인 카드 수로 센다. 기본값은 2이고 설정으로 바꿀 수 있다. 유닛은 한 번에 카드 하나만 가진다.
- 일시정지 중에는 쓰기 권한(변경안 제출) 유닛에게 새 카드를 주지 않는다. 읽기 전용 유닛은 받는다. 이미 진행 중인 카드는 끝낼 수 있다.
- 허용하는 상태 이동: 진행 중에서 검토, 완료, 막힘, 할 일로. 검토에서 완료 또는 할 일로. 막힘에서 할 일로. 할 일에서 진행 중은 배정으로만 가능하다.
- 검토에서 반려된 카드는 진행 중이 아니라 할 일로 돌아간다. 진행 중으로 되돌리면 동시 실행 한도를 넘길 수 있고, 검토자 카드와 자리를 다투다 멈출 수 있기 때문이다.
- 카드 등록은 중복 id, 없는 선행 카드, 순환 의존을 검사하고, 문제가 있으면 아무것도 등록하지 않는다.

## 자동 테스트와 TypeScript 설정 (2026-10-13)
- API를 부르지 않는 결정적 로직(보드 규칙)에는 자동 테스트를 둔다. Node 기본 기능(node --test)을 쓰며 npm test로 실행한다. 테스트 파일은 소스 옆에 *.test.ts로 둔다.
- TypeScript 7은 Node 타입을 자동으로 불러오지 않는다. tsconfig.base.json에 types: ["node"]를 명시한다.

## 영역 (2026-10-14)
- Planner는 계획할 때 먼저 작업을 크게 나눈 영역을 정하고, 각 영역 안에 유닛을 하나 이상 배치한다. 영역은 이름, 목표, 파일 범위를 가진 묶음이며 별도의 LLM 세션이 아니다.
- builder는 영역 하나에 반드시 소속한다. reviewer와 integrator 같은 유닛은 영역에 소속하거나, 소속 없이(null) 모든 영역에 걸쳐 일할 수 있다.
- 유닛과 카드의 쓰기 범위는 자기 영역의 쓰기 범위 안에 있어야 한다. 소속 없는 유닛과 카드는 어느 영역의 쓰기 범위 안이면 된다.
- 영역끼리 쓰기 범위가 겹치는 곳은 Planner가 공유 경로로 명시한 안에서만 허용한다. 공유 경로가 서로 다른 영역의 유닛이 같은 파일을 건드리는 핵심 장면의 무대가 된다.
- 영역에 소속된 유닛은 자기 영역의 카드만 가져간다. 소속 없는 유닛은 모든 영역의 카드를 가져간다. 영역이 달라도 동시 실행 한도는 함께 적용한다.
- 범위 항목은 정확한 파일 경로 또는 슬래시(/)로 끝나는 폴더 접두어 두 가지만 쓴다. 와일드카드는 쓰지 않는다. 절대 경로, 상위 폴더(..), 역슬래시, 드라이브 문자는 거부한다.
- 영역은 계획 승인 뒤 한 번만 등록하며, 유닛과 카드보다 먼저 등록해야 한다. 영역 수와 영역당 유닛 수에는 상한을 두지 않는다.
- 대시보드는 영역별 가로줄이 있는 칸반 보드로 그린다.

## 작업공간 (2026-10-14)
- 작업공간은 packages/server/src/workspace에 둔다. 파일 버전은 메모리에서 관리하고, 적용된 내용은 사용자가 정한 작업 폴더에도 쓴다.
- 작업 폴더가 없으면 만들고, 있으면 비어 있어야 한다. 운영체제가 자동으로 만드는 파일(.DS_Store, Thumbs.db, desktop.ini)은 비어 있는 것으로 본다. 기존 파일이 있는 폴더는 거부하며, 기존 코드 수정은 로드맵으로 둔다.
- 파일 버전은 없는 파일이 0이고 적용될 때마다 1씩 오른다. 변경안의 기준 버전이 현재 버전과 같을 때만 적용한다.
- 변경안은 전부 적용되거나 전부 거부된다. 디스크 쓰기가 중간에 실패하면 이미 쓴 파일을 되돌리고 오류를 낸다.
- 거부 사유는 빈 변경안, 잘못된 경로, 잘못된 기준 버전, 같은 경로 중복 제출, 쓰기 범위 밖, 버전 불일치 여섯 가지다.
- 버전 불일치로 거부될 때 그 파일을 마지막으로 고친 카드를 함께 알려 준다. 오케스트레이터는 이 정보로 충돌 이벤트를 만든다. 두 카드가 같은 새 파일을 만들려 하는 경우도 같은 방식으로 감지된다.
- 파일 경로는 범위 항목 규칙을 따르되 폴더 접두어는 파일로 쓸 수 없다. 작업 폴더 밖으로 나가는 경로는 검증 단계와 디스크 경로 계산 단계에서 두 번 막는다.
- 한계: 파일 크기 제한과 심볼릭 링크 대응은 아직 없다. 작업 폴더는 비어 있는 상태로 시작하고 RallyPoint만 쓰기 때문에 지금은 두지 않는다.

## 유닛 실행기 (2026-10-14)
- 유닛 실행기는 packages/server/src/runner에 둔다. 카드 하나를 유닛이 한 번 수행하는 함수(runCard)이며, 보드는 건드리지 않고 결과만 돌려준다. 보드 이동과 이벤트는 오케스트레이터가 맡는다.
- 모델 호출은 LlmClient 인터페이스 뒤에 둔다. 실제 API 연결(Anthropic SDK)은 anthropic-client.ts 한 곳뿐이고, 테스트는 미리 정한 답을 돌려주는 가짜 클라이언트로 한다. 테스트에서 API 비용이 들지 않는다.
- 모델은 도구 호출로만 답하게 시스템 지시로 요구한다. 현재 모델(claude-sonnet-5-5)은 tool_choice any를 지원하지 않아(실제 호출에서 400 확인) auto로 두고, 도구를 부르지 않은 답은 형식 오류로 보아 다시 묻는다. 쓰기 권한 유닛은 propose_changes와 report_blocked, 읽기 전용 유닛은 submit_report와 report_blocked만 받는다. 읽기 전용 유닛에는 파일을 바꾸는 도구 자체를 주지 않는다.
- 호출 전에 카드 범위 안의 파일 내용과 버전을 기록해 모델에게 보여 주고, 모델이 낸 변경안의 기준 버전으로 쓴다. 보여준 적 없는 새 파일은 0이다. 모델이 답하는 동안 다른 카드가 같은 파일을 바꾸면 작업공간이 막고, 실행기는 충돌(conflict)과 충돌 상대 카드를 돌려준다.
- 실제 쓰기 범위는 카드의 쓰기 범위 중 유닛의 쓰기 범위 안에 드는 것만이다. 보여줄 파일이 너무 많으면(기본 40만 자) 호출하지 않고 실패로 돌려준다.
- 결과는 완료, 막힘(모델이 못 한다고 보고), 충돌, 실패 네 가지다. 실패 사유는 호출 실패, 형식 오류 반복, 답 잘림, 문맥 과다, 변경안 거부다.
- 재시도는 실행기 한 곳에서만 한다(SDK 자동 재시도는 끈다). 일시적 오류(연결 끊김, 408, 409, 429, 5xx)는 1초, 2초 간격으로 늘려 총 3번까지 다시 보낸다. 키 오류 같은 영구 오류는 바로 실패한다. 형식에 맞지 않는 답은 이유를 덧붙여 다시 묻는다. 답 잘림과 범위 위반은 같은 결과가 나오므로 다시 하지 않는다.
- 토큰 사용량은 시도마다 합산해 결과에 담는다. 오케스트레이터가 사용량 이벤트와 비용 추정에 쓴다.
- 실제 API 확인은 smoke-runner로 한다(npm run build 뒤 node --env-file=.env packages/server/dist/smoke-runner.js). 비용이 들므로 사용자가 직접 실행한다.
- 한계: Planner와 Scheduler는 파일을 바꾸지 않고 계획을 내는 다른 도구가 필요해서 이 실행기 대상이 아니다. 스트리밍과 프롬프트 캐시는 아직 쓰지 않는다.
